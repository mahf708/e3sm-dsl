\begin{abstract}
We describe a diagnostic expression language that lets a derived diagnostic be requested in the output configuration instead of added to model source code. A standalone parser turns a string containing a mathematical expression into a syntax tree. The model checks this tree against a controlled vocabulary and translates it into a graph of diagnostics already compiled into the model, which evaluates the original expression. The evaluation runs inside the model's time loop, on model state resident on the GPU, before any remapping or temporal accumulation. We implement the system in the C++ atmosphere component of the Energy Exascale Earth System Model (E3SM). Expression-produced fields agree with offline reconstructions bit for bit or to floating-point round-off, and add no end-to-end cost separable from the model's run-to-run variability at the expression depths we test. Three miniature experiments --- a doubly periodic case, a conditional high-cloud workflow, and a surface-coupling debugging investigation --- show that representative diagnostics from each can be written as expressions and evaluated at runtime.
\end{abstract}

\introduction
\label{sec:intro}

An Earth system model is a set of equations, spatially discretized and temporally stepped forward. The model state comprises tens to a few hundreds of fields on a three-dimensional grid, updated every time step. Storing the full model state at every time step is impractical due to the sheer volume of data generated. For example, the atmosphere component of the latest release of the Energy Exascale Earth System Model (E3SM), at its standard nominal 1$^\circ$ (about 100\,km) horizontal resolution, has 21\,600 columns and 80 levels with a time step of 30 minutes. This amounts to about $7$\,MB per three-dimensional field per sample in single-precision floating-point format ($21\,600\times80\times4$ bytes). Carrying $O(100)$ state fields puts a single snapshot near $0.7$\,GB, and writing one every time step for a simulated year ($17\,520$ samples) comes to about $12$\,TB. Horizontal resolution refinement makes the data volume grow in a roughly cubic manner with respect to the refinement factor \citep{schar_kilometer-scale_2020}, assuming horizontal refinement is uniform and the temporal resolution is modified to ensure stability, while the vertical resolution remains constant. The 3.25\,km global storm-resolving configuration of the E3SM atmosphere \citep{caldwell_convectionpermitting_2021}, with about 25 million columns and 128 levels, needs about 13\,GB for a single three-dimensional field per sample, nearly $2000$ times as much, before its shorter time step is taken into account.

In practice, the raw archive is never saved in its entirety. Instead, a carefully chosen subset of the model state is written according to an output list agreed upon in advance, supplemented with developer-written derived diagnostics, at a specified cadence and precision. Customarily, the set of all possible output variables is hard-coded in the model, and which ones are output is determined at runtime. Adding a new variable, however, cannot be done without modifying the source code, and such changes are often needed for community-driven model intercomparison projects or for specific scientific questions. When the source is not changed, the common alternative is to write every input the derived quantity needs and compute it in post-processing, which further amplifies the output volume and the time the model spends writing it. The final output set is usually settled by logistics (how much disk is available and for how long), but it crucially also settles which questions the output can answer. The output list acts as an observation operator applied to the simulated trajectory.

The arrangement is comfortable while models have coarse resolution, but at storm- and cloud-resolving resolutions, challenges arise due to both the output volume \citep{balaji_requirements_2018} and the evolving set of questions we want to ask of the model. A coarse global model is typically evaluated for its mean state, the seasonal cycle, and top-of-atmosphere energy balance, where monthly or daily means of a fixed field list serve the purpose well enough. A kilometer-scale model enables further specialized evaluations, e.g., the organization of convection, updraft and downdraft statistics, cloud lifecycles, precipitation and wind extremes, and boundary-layer evolution \citep{caldwell_convectionpermitting_2021,donahue_exascale_2024}. The latter evaluations require conditional means, higher moments, distributions, event frequencies, threshold exceedances, and quantities tracked across time steps, which are not captured by simple averages. These requirements need samples co-located in space and time at every model time step, conditioning on masks the model forms on its grid, and in some cases state carried from one step to the next. None of these quantities commutes with the averaging and remapping that make output affordable either, so each one has to be formed at a particular point in the pipeline. For example, a cloud mask diagnosed on the native grid and then remapped differs from a mask applied after remapping, and the covariance of two fields within an averaging window is not recoverable from their window means. The definition of a derived quantity therefore depends on the ordering of averaging and remapping, so an output list that fixes the order also fixes the observables. To track an evolving set of observables, an archived dataset must also grow and store different things. Ultimately, these two needs pull simulation campaigns in opposite directions and limit scientists' ability to conduct their inquiries.

Moreover, model output is increasingly used as training data for machine learning. Component and full-model emulators stand in as economical alternatives to physics models; process emulators replace uncertain or expensive parameterizations inside a running model; output emulators map model state to the quantities users need from it, whether by downscaling, bias correction, projection onto impact space, or forming specialized diagnostics from a reduced state; and foundation models are fit to corpora assembled from many sources.
Training datasets often need a different selection from the model than human analysis does. A full-model emulator may be trained on far fewer variables than are routinely written (often specialized ones), but at higher frequency, and process emulators need quantities that are rarely written at all: tendencies, fluxes, co-located input--output pairs, and process-level state; an output emulator, in turn, needs the specialized diagnostics it is to reproduce, sampled together with the state it maps from. A training set prepared from model output has the same problem: whatever the preparation discards is not available to the model being trained.

All of this points to rethinking how model output is designed. In this manuscript, we propose an approach with three elements: (i) a diagnostic is written as a mathematical expression, a composition of a small set of typed operators; (ii) the expression is evaluated by the model at runtime, while the full state is still in memory and before anything is averaged, remapped, or written; and (iii) the operators are the model's own, acting on its representation of the state --- its grid, vertical coordinate, units, and masks. The value is then accumulated in memory and written at whatever cadence the output requires, so sampling (every step) is decoupled from writing. When implemented, such a system allows a scientist to define a variable or product and get it from the model without touching the source code: instantaneous or averaged, over an arbitrary time period, mapped, masked, reduced, or redefined.

\subsection{Related works}
\label{sec:related_works}

Outside Earth system modeling, other simulation domains routinely reduce data volume before it is written, and several give users composable operators over the live state to do it with.
Molecular dynamics composes on-the-fly computations and time averages, so a study need not write trajectories \citep{thompson_lammps_2022}. Computational fluid dynamics evaluates user-written field expressions at run time, with dimensions and region masks, and can decline to store the result \citep{weller_tensorial_1998}. Astrophysics analysis frameworks let a user define a derived field as a formula over other fields, which may themselves be derived, with physics units propagated automatically through each definition \citep{turk_yt_2011}. Runtime-analysis frameworks provide expression systems, including derived fields that are just-in-time compiled, i.e., translated to machine code while the program runs, immediately before they are evaluated \citep{ayachit_paraview_2015,childs_ascent_2022,godoy_adios_2020}. Compiling a declarative mathematical specification down to domain-specific code is long-established in finite-element software \citep{alnaes_unified_2014}, and separating what is computed from how it is scheduled is standard practice in domain-specific compilers \citep{ragan-kelley_halide_2013}.

Within Earth system modeling, the capability appears at four placements with respect to the model's state in memory. We call the point at which data leave the model's memory, by being written to disk or handed to a program outside the model, the \emph{persistence boundary}. Below, the first placement acts before it, the second before or after it depending on where it does its work, and the last two after it.

\emph{(1) Diagnostic managers in the model source.} These expose a registered catalogue with reductions \citep{valcke_flexible_2012,danabasoglu_community_2020,kern_diagnostic_2016,adams_lfric_2019}, conditional sampling and budgets available through specialized namelist interfaces \citep{wan_condidiag10_2022}, and arbitrary code through plugin interfaces \citep{hartung_icon_2025,kern_diagnostic_2016}. These diagnostic managers in the model source sit closest to the state by definition. With a catalogue, a quantity not compiled into it requires a source code change to be available. CondiDiag goes further: a new condition, threshold or sampling checkpoint is a namelist edit, and it samples at checkpoints inside the physics sequence of substeps of an atmosphere time step, but adding new metrics or quantities requires source code edits \citep{wan_condidiag10_2022}. A plugin interface such as ComIn, once the model is built with it, needs no rebuilding of the model for a new plugin, and a Python plugin no compilation at all, but what the user supplies is executable code rather than an expression \citep{hartung_icon_2025}.

\emph{(2) I/O middleware.} These are libraries that sit between the model and the file system; they transform fields on their way to the file (the write path). The XML Input/Output Server (XIOS) provides arithmetic and elementary functions on fields, temporal operations and domain transformations, and can run inside the model's processes or on separate server processes \citep{meurdesoif_xios_2017,yepes-arbos_evaluation_2022}; MultIO provides configurable in-memory processing pipelines \citep{sarmany_multio_2024}; and the Adaptable Input/Output System (ADIOS2) supports derived variables computed by the writer \citep{godoy_adios_2020}.

\emph{(3) Streaming architectures.} These publish model state by handing it to consumers outside the model while a simulation runs. For example, nextGEMS makes common data handling and analysis a first-order part of kilometer-scale multi-model development, EVE frames simulation and data services as a federated infrastructure, and the Destination Earth Climate Digital Twin couples high-resolution production with streaming and downstream processing through One-Pass and AQUA \citep{segura_nextgems_2025,stevens_earth_2024,doblas-reyes_destination_2026,grayson_statistical_2025,nurisso_aqua_2026}.

\emph{(4) Post-processing on the archive.} Offline analysis is supported by mature tooling in which fields are labeled objects and operators compose over them \citep{zender_analysis_2008,hoyer_xarray_2017,zhang_e3sm_2022}, and a scientist can express essentially any quantity there without touching model source code, given sufficient output. Post-processing, however, sees only what was written, not the full model state. It reproduces a quantity exactly only when that quantity is fully determined by what was written. For example, users generally do not write process rates, which depend on the order in which processes act within a step and on any limiters or conservation fixers applied in between --- none of which is recoverable from the written state.

Time averaging and choosing which snapshots to keep are established forms of reduction before persistence, and they are already part of every output configuration. In global kilometer-scale modeling, where the archive cannot keep up with the model, more elaborate reductions --- conditional statistics, moments, distributions --- are now moving before the persistence boundary too. Other applications, such as object tracking and observation simulators that need high spatial and temporal resolution along particular objects or directions, still write more output than ever, and will continue to need to.

Each of the three elements of our proposed approach (composable operators, evaluation before the persistence boundary, and operators that are the model's own acting on its representation of the state) exists somewhere in the above examples, and the first two are fairly common together, as in I/O middleware. Two recent models, Dedalus and Oceananigans, have all three elements. There, a user writes an output quantity as an expression in the script that defines the run, and it is evaluated during the run against the model's operators, with Oceananigans compiling the composition to a GPU kernel \citep{burns_dedalus_2020,ramadhan_oceananigansjl_2020}. They obtain this capability from the symbolic and operator systems of their host languages, Python and Julia, which a compiled production component does not have.

Because I/O middleware and streaming architectures also run while the simulation runs, the distinction we draw is between whose code computes the diagnostic and on which representation of the state, not between online and offline analysis. Each model component has its own grid, vertical coordinate, area weights, and rules for masking and renormalization. For a quantity that depends on these conventions, such as a mass-weighted vertical integral or a horizontal mean over valid cells only, the implementation is part of the definition, and the component's code is the reference implementation. For that reason we follow \citet{childs_terminology_2020} in avoiding ``in situ,'' whose established usage covers analysis of data that the simulation hands over in a generic mesh representation, and we write ``in-model'' for evaluation by the component's own code on its data structures.

\subsection{Contributions}
\label{sec:contribs}

We implement the approach described above in EAMxx, the C++ atmosphere component of E3SM \citep{donahue_exascale_2024}, written with Kokkos for performance portability across CPUs and GPUs \citep{trott_kokkos_2022}. We call it the \emph{host model} from here on, because the system is designed so that other E3SM components can host it as well. Figure~\ref{fig:arch} shows the system, and Table~\ref{tab:terms} defines the terms we use for its parts in this manuscript. A user writes a derived quantity as an expression over model fields in the output configuration. When the output stream is set up, a standalone parser turns the string into a syntax tree; the host model checks every name and operation in the tree against a list of operations it supports, and translates the tree into a graph of its existing compiled diagnostics, i.e., C++ routines already in the model that compute derived fields from other fields. The operators are familiar ones for atmospheric modeling, for example, selection of a model level and vertical interpolation to pressure or height surfaces; horizontal, zonal and vertical reduction; vertical derivatives; conditional sampling; histograms; arithmetic; and a one-step temporal shift. Horizontal regridding is not among them because it is already a stream setting (Sect.~\ref{sec:design}). Composed with the stream's instantaneous, mean, minimum and maximum accumulation, they cover many of the kinds of quantity named in Sect.~\ref{sec:intro} (conditional means, moments, distributions, threshold exceedances and one-step temporal differences), though not yet output at fixed sites or along a track (Sect.~\ref{sec:conclusions}) or a quantity that exists only inside a parameterization (see below).

Our system has four properties. It is \emph{user-defined}: the quantity is named in a configuration file, not added to model source code, so asking a new question does not require new source code edits. It is \emph{in-model}: each expression is evaluated at the end of the step, inside the component's own output path (every step in a stream that accumulates over time, every output step in an instantaneous stream), on the model's in-memory fields and before the stream's remapping and temporal accumulation --- so a quantity can be formed before the reductions that would lose it, though not between two parameterizations (for now). It is \emph{GPU-friendly}: the code that executes is the model's Kokkos kernels operating on the same device-resident arrays the model's processes use, so nothing is copied to the host and no second array model is introduced. It has a \emph{small, controlled vocabulary}: the operators compose wherever their contracts and the stream's evaluation schedule are compatible, but only operators the host model provides can be used, so every expression that can be formed is one the model can check.

The in-model property also sets the scope of what an expression can see. An expression can reference any field registered with the host model's field manager on the stream's grid, including the prognostic state, the fields that processes register to exchange with one another, as well as other diagnostics and expressions. What an expression cannot reach is a quantity that exists only inside a parameterization --- an individual microphysics conversion rate, for instance, or a rate as it was before a conservation fixer modified it --- because such values live in local arrays that are discarded before the end of the step. Exposing one such quantity still requires a source change that registers through a central field manager (see Sect.~\ref{sec:design}). That change is needed once per input quantity, however, after which every derived combination of it is a configuration choice. The host model still hard-codes which quantities are available; the expression system makes the operations on them configurable.

This implementation is a start for E3SM rather than a finished system. We do not demonstrate a model-independent language, port the capability to another component yet, implement an optimizer or a typed intermediate representation, or fuse expressions for performance. Our goal is to bring this capability soon to Omega, the C++ ocean component of E3SM \citep{petersen_ocean_2026}, and from there to the other E3SM components. Additionally, we aim to expand the vocabulary to cover more derived quantities and operations that scientists commonly use in their analyses on an as-needed basis.

\section{Design and implementation}
\label{sec:design}

\emph{Fields as contracts.} The host model holds its state in field objects rather than raw arrays.
\begin{equation}
  F_\sigma = (x, \chi;\ \nu, \tau, \sigma)
  \qquad
  \sigma = (g,l,d,u,\mu)
  \label{eq:field}
\end{equation}
A field $F$ carries its numerical storage $x$ and, if it has one, a validity mask $\chi$ marking the entries that hold data, together with a name $\nu$, a time stamp $\tau$ recording when its values were last updated, and a contract $\sigma$. The contract contains a grid $g$, a labeled layout $l$ (the named dimensions, such as columns and levels), a data type $d$, units $u$, and a flag $\mu$ recording whether the field has a mask. The contract is fixed once the stream is set up, whereas $x$ and $\chi$ change from step to step. Every field, whether it is a model variable, an intermediate defined by an alias, or an expression written to file, has both a name and a contract --- the name is how it is looked up, and the contract is how operations on it are checked. Every operation on a field enforces the constraints its contract encodes. For example, two fields can be added only if their units agree; multiplying them multiplies their units; a vertical reduction removes the vertical dimension tag; interpolating to a pressure level introduces a mask where the level lies outside the column. Like prognostic processes in the model, diagnostics take fields as input and produce fields as output. A control driver runs these processes in dependency order. Because the output of a diagnostic is itself a field, it can be used as input for subsequent diagnostics, so diagnostics compose with no extra machinery. Redundant calculation is avoided both within and across output streams. First, a diagnostic keeps track of the time stamps of each input field, so it skips the calculation entirely if none of them has changed since the last evaluation. Second, all output streams use a centralized diagnostic repository keyed by the diagnostic field name, so a stream does not recompute a diagnostic another stream has already computed.

\emph{Output pipeline.} At each step of a stream that accumulates over time (and at each output step of an instantaneous stream), the output driver evaluates diagnostics on the model's grid, then applies optional vertical remapping, then optional horizontal remapping, then updates the stream's temporal accumulator, and, at the stream's output frequency, writes through SCORPIO \citep{krishna_scorpio_2025}:
\begin{equation}
  Y = \mathcal{A}_t\,\mathcal{R}_\text{h}\,\mathcal{R}_\text{v}\,\mathcal{D}_\text{e}[X(t),H(t)],
  \qquad
  H(t+1) = U[X(t),H(t)].
  \label{eq:pipeline}
\end{equation}
Here $X(t)$ is the model state at step $t$; $\mathcal{D}_\text{e}$ is the diagnostic stage, which evaluates every requested expression; $H(t)$ is the state that stage carries from one step to the next via a copy that $U$ performs; $\mathcal{R}_\text{v}$ and $\mathcal{R}_\text{h}$ are the vertical and horizontal remapping operators; $\mathcal{A}_t$ is the temporal accumulation (instantaneous, mean, minimum or maximum over the output window $W$); and $Y$ is what the stream writes. Absent stages resolve to the identity. That an instantaneous stream evaluates only at its output steps matters for one operator at present: the one-step shift of Table~\ref{tab:vocabulary} keeps the value its operand had one model step earlier, so a shift of an expression is rejected at stream setup in an instantaneous stream whose output interval is longer than one step. The written expression controls $\mathcal{D}_\text{e}$, and stream settings control the rest. $\mathcal{R}_\text{v}$ is not the \texttt{interp} method of Table~\ref{tab:vocabulary}; it is a more general vertical remapping operator per stream: it maps every written field that has a level dimension to pressure levels read from a file, after all expressions have been evaluated, whereas \texttt{interp} produces one level of one field inside $\mathcal{D}_\text{e}$, where the result can be the operand of further operations. A mean averages each element over the samples in $W$ that hold data, and for a conditional sample \texttt{X.where(c)}, written $\phi|c$ with $\phi$ the field \texttt{X}, this is the pooled conditional mean:
\begin{equation}
  \mathcal{A}_t[z] = \frac{\sum_{t\in W} v_t\,z_t}{\sum_{t\in W} v_t},
  \qquad
  \mathcal{A}_t[\phi|c] = \frac{\sum_{t\in W} c_t\,\phi_t}{\sum_{t\in W} c_t}.
  \label{eq:mean}
\end{equation}
Here $v_t$ is 1 where $z_t$ is not the fill value and 0 where it is, so the count is taken from the values rather than from a mask, and $c_t$ is 1 where the condition holds and $\phi$ and the compared fields are valid. Like mean, minimum and maximum stream accumulations skip fill values. The pooled mean is a ratio of sums over the window, not a mean of per-step conditional means; the two differ once a spatial reduction, as in \texttt{X.where(c).mean('col')}, comes before $\mathcal{A}_t$, because each step then contributes one conditional mean with equal weight. In general, remapping and averaging do not commute with nonlinear operations that are encoded in the diagnostic expressions. In this pipeline, the nonlinear operations of an expression always sit before remapping and averaging. Figure~\ref{fig:arch} separates what happens once, when a stream is set up, from what happens at every step, and places both relative to the persistence boundary.

\emph{Parser and registry.} Composition without a formal grammar quickly becomes ambiguous, so we wrote a parser, \dexpr, for E3SM. It consists of a lexer, which splits the string into tokens (names, numbers, operators and brackets); a \citet{pratt_top_1973} parser, which groups the tokens according to operator precedence into an abstract syntax tree (AST); a renderer that prints a syntax tree back to canonical text; and a call validator. It is a minimalist C++ library with no dependencies, and it does not know what a field, a grid, or a time step is. The host model decides how each function name is mapped to a concrete diagnostic, through a function registry in which it declares each callable with its name, its number of arguments, its accepted keywords, and an example of the call as written. The registry validates itself when it is constructed, checking that each example parses, calls the function that declares it, and satisfies that function's argument and keyword rules. The host model builds its registry when it first translates an expression. The grammar is thus shared and the meaning of each operation is local to the host, so two components can share a parser without sharing a single physics operator.

\emph{Surface syntax.} Our syntax follows xarray \citep{hoyer_xarray_2017} spelling where possible and available. A stream's configuration lists the fields it writes under \texttt{field\_names}. An entry there may be a model field name or an expression; an expression must be given a name with \texttt{:=}, because the expression itself may not be a valid NetCDF \citep{rew_netcdf_1990} variable name. Entries under \texttt{aliases} are named expressions that are computed and can be used by name in other expressions, but are not written, i.e., do not cross the persistence boundary. The only difference between the two lists is whether the result is written: \texttt{warm\_T} below could equally be listed under \texttt{field\_names}, and an expression needs no alias to contain a conditional.
\begin{verbatim}
fields:
  physics_pg2:
    aliases:
      - warm_T         := T_mid.where(T_mid>273.15)
    field_names:
      - rho_air        := p_mid/(Rair*T_mid)
      - warm_T_colavg  := warm_T.mean('lev')
\end{verbatim}
The variable \texttt{rho\_air}, the air density from the ideal gas law, carries \texttt{p\_mid/(Rair*T\_mid)} as its \texttt{alias\_of} attribute, and its units are derived from those of its operands. Operands may be model fields, other expressions, named physical constants such as \texttt{P0}, \texttt{Rair} and \texttt{gravit} in arithmetic, or numeric literals, which may be negative. A name that is both a model field and a physical constant is rejected when the stream is set up, because it cannot be told which was meant. Precedence is conventional, so \texttt{qc+qv*p\_mid} means \texttt{qc+(qv*p\_mid)} --- which is in fact rejected at construction due to units mismatch --- whereas \texttt{(qc+qv)*p\_mid} is admissible. Appendix~\ref{app:grammar} gives the formal grammar of the requests the host model accepts, and Table~\ref{tab:vocabulary} gives the arguments each method accepts. We note that, while \dexpr\ itself parses more, the host model accepts only this subset for now. There are no loops, user-defined functions, mutation, external state, or dynamic code loading, and every operation has a compiled implementation, a field contract, and a unit test. Other than negation and the backward tendency, each operation in Table~\ref{tab:vocabulary} is a primitive $D_k$, one of the operators the diagnostic stage $\mathcal{D}_\text{e}$ of Eq.~(\ref{eq:pipeline}) composes. Each is applied in two steps: a signature ($\Sigma_k$) that asks, from the contracts alone, whether a request means anything and what contract its result would carry, and, where that succeeds, the computation of the numbers,
\begin{equation}
\begin{aligned}
  \Sigma_k &: (\sigma_1,\ldots,\sigma_n;\ \theta)
        \rightharpoonup (\sigma'_1,\ldots,\sigma'_m),\\
  D_k(\theta) &: F_{\sigma_1}\times\cdots\times F_{\sigma_n}
        \longrightarrow F_{\sigma'_1}\times\cdots\times F_{\sigma'_m}.
\end{aligned}
\label{eq:ops}
\end{equation}
Fields $F_\sigma$ carry a contract $\sigma$ as defined in Eq.~(\ref{eq:field}); and $\theta\in\Theta_k$ is the primitive's non-field arguments, e.g., the level index in \texttt{X.isel(lev=-1)}; the half arrow $\rightharpoonup$ marks a partial map, one that is undefined for some inputs. The signature does not succeed on requests the model rejects, such as adding two fields whose units differ; the output contract is computed by the primitive, not inherited from the inputs. The signature is checked once, on the host, when the expression is translated at stream setup; the second line is what runs on the device each time the diagnostic is evaluated. All primitives depend only on their inputs at the current step (the only exception is \texttt{shift}, whose output is its part of $H$ in Eq.~(\ref{eq:pipeline})).

\emph{Building the diagnostic graph by name.} A request reaches the host model's output manager, the part of the model that sets up and runs the output streams, as a string. The manager splits off the optional \texttt{name :=} prefix and passes the remainder to \dexpr, which splits it into tokens and parses them into a syntax tree; the tree is then checked against the host model's registry. Only the root of the tree, the outermost operation, is translated directly, into one diagnostic and its parameters. Each of the root's operands is printed back to canonical text, and that text is recorded as the name of an input field the diagnostic needs. The output manager's ordinary dependency resolution then finds that no field of that name exists yet and asks the diagnostic-construction routine (the factory that builds a diagnostic from its name) to provide one; because the name is itself an expression, it is parsed in turn, and so on until every operand is a model field or a number (Fig.~\ref{fig:dag}). The whole diagnostic graph is thus built by resolving names, using no data structure the output manager does not already have. Because operands are rendered canonically, an operand's name is a reliable key: \texttt{qv > 0.01} and \texttt{qv>0.01} name the same diagnostic when nested, and so do \texttt{1e-4} and \texttt{0.0001}. An alias, in contrast, is keyed by its own name, so \texttt{warm\_T} and an inline \texttt{T\_mid.\bk where(T\_mid>273.15)} in another request of the same stream build two copies of the same diagnostic (Sect.~\ref{sec:conclusions}). Checking is layered so that a failure is reported by the layer that knows why it fails rather than by a higher or lower layer. As such, \dexpr\ catches malformed syntax, unknown functions, wrong numbers of arguments, and keyword errors; the host-model translation layer catches operators with no diagnostic, comparisons outside \texttt{where}, and expressions whose result is not a field; diagnostic construction catches incompatible units, layouts, data types, and grids; and stream setup catches unnamed expressions, duplicate aliases, unresolvable dependencies, and integer output. No layer silently repairs a request, and there is no algebraic rewriting. The variable in the output file carries the user's output name, the derived units, and an \texttt{alias\_of} attribute holding the requested expression, which is expression-level provenance rather than the fully resolved graph; complete reconstruction additionally requires the stream configuration and the run record.

\emph{Specialized operators.} The operators of Table~\ref{tab:vocabulary} are generic, but nothing in the registry requires an operator to be. A component can register one that encodes its own scientific conventions, and that operator then composes with the generic ones like any other. We illustrate this flexibility with an example operator: \texttt{X.aerocom('top')} samples a field \texttt{X} where a passive satellite imager sees cloud, at its top (\texttt{'bot'} samples at its base, as if the satellite imager is at the Earth's surface), following the AeroCom recommendation for comparing models of aerosol--cloud interaction with satellite retrievals \citep{quaas_aerosol_2009}. Per column, it is the weighted vertical sum
\begin{equation}
  x = \sum_k X_k\,\Phi_k\,w_k,
  \label{eq:aerocom}
\end{equation}
in which $w_k$ is the probability that level $k$ is the first cloudy level seen from above (or from below), computed from the model's cloud fraction and condensate under the maximum-random overlap assumption \citep{tiedtke_ecmwf_1979}, and $\Phi_k$ is 1 or, with \texttt{phase='liq'} or \texttt{'ice'}, the share of the level's condensate in that phase. With the reserved name \texttt{mask} as receiver, $X$ is 1, so \texttt{mask.aerocom('top')} is the cloud fraction seen from above. To illustrate the usage of multiple composable diagnostic operators together, the in-cloud droplet number concentration per unit volume at liquid cloud top, for instance, is requested as
\begin{verbatim}
fields:
  physics_pg2:
    aliases:
      - air_density  := pseudo_density/dz/gravit
      - nc_incloud   := nc*air_density/cldfrac_tot.where(cldfrac_tot>0)
    field_names:
      - cdnc_top_liq := nc_incloud.aerocom('top', phase='liq')
\end{verbatim}
in which \texttt{air\_density} is the air density from the layer's mass and thickness, and the \texttt{where} keeps the division by cloud fraction away from cloud-free levels, which carry no weight and are skipped. The weights $\Phi_k w_k$ are themselves a diagnostic, \texttt{cldfrac\_tot.\bk aerocom\_weights('top')}, on which \texttt{aerocom} depends by name, so every request at the same position and phase shares one computation of them per step. A cloud-top quantity is defined by the overlap assumption and by the thresholds that decide which levels are cloudy, and those belong to the model. Written once as an operator, the definition is applied identically to whatever field a user asks to see from cloud top (or cloud bottom).

\section{Demonstrations}
\label{sec:demos}

We use three small experiments to show the capability in settings a scientist would recognize. Two are reduced versions of workflows from scientific studies, one published and one in review, and the third comes from an investigation of surface coupling. Each is cut down to the duration and resolution its operators need. In each experiment, we check the expression output against an independent reconstruction from every-step output of the same run; regression tests in the model additionally compare masked and conditionally sampled diagnostics with hand-computed values, including empty masks, chained conditions and valid-sample counts. All runs use NVIDIA A100 GPUs on the Perlmutter system at the National Energy Research Scientific Computing Center (NERSC). The expressions add no measurable cost: in one-day ne30pg2 runs, each repeated five times, the median run time with a daily-averaged stream of five expression diagnostics differs by $+0.04\,\%$ from that of a baseline stream of two model fields, well inside the $0.8\,\%$ spread of the repeated baseline runs. Here ne30pg2 denotes E3SM's cubed-sphere grid with $30\times30$ spectral elements on each cube face and $2\times2$ physics columns per element (21\,600 columns, about 1$^\circ$); ne4pg2 is the same construction with $4\times4$ elements per face (384 columns, about 10$^\circ$). The cost grows with expression depth, however, because each diagnostic in a graph computes and stores its own intermediate field; we discuss future performance work in Sect.~\ref{sec:conclusions}.

The first experiment is a reduced instance of the doubly periodic configuration of \citet{bogenschutz_high_2025}: a $50\times50$\,km radiative--convective-equilibrium domain with 100 columns, 128 levels and a 100\,s time step. We request the horizontal-mean temperature profile \texttt{T\_mid.\bk mean('col')}, the horizontal mean of its square, \texttt{T2.\bk mean('col')} with \texttt{T2 := T\_mid*T\_mid}, and the square of the horizontal mean, \texttt{Tbar*Tbar} with \texttt{Tbar := T\_mid.\bk mean('col')}, together with the same moments of \texttt{qv} and its mass-weighted column mean \texttt{qv.\bk mean('lev',\bk weights='dp')}. Figure~\ref{fig:demos}a shows the temperature profile and its horizontal spread, formed from the moments, over the last eight days of a 20-day run. The moments match the same reductions of every-step output to round-off, and their files are 6212 times smaller than the every-step temperature and specific humidity needed to form them offline. Limited-domain studies often need such domain-mean quantities, which the online reductions supply without writing a single three-dimensional field.

\subsection{Conditional high-cloud products}
\label{sec:cess2}

The second experiment is a one-day instance of the conditional high-cloud workflow of \citet{beydoun_dissecting_2021} \todo{cite 2026 paper}, which examines the response of tropical anvil cloud to surface warming. It is a global atmosphere-only simulation with prescribed sea surface temperature and sea ice on the ne4pg2 grid, with 384 columns, 128 levels and a one-hour time step.
We request the model-side operations of that workflow: the cloud condition $q_i+q_c>10^{-5}$, conditional samples such as \texttt{qi.where(qi+qc>1e-5)}, a conditional vertical derivative, and a product of conditionally sampled quantities, accumulated over 12\,h. Figure~\ref{fig:demos}b shows one of them, the microphysics ice tendency in cloudy sky. Dropping the \texttt{where} from the same request gives the all-sky profile, which is about 18 times smaller in magnitude because it also averages the cloud-free columns. A negative threshold, a chained condition and a product of two conditional samples match every-step reconstructions bit for bit, with identical masks and valid-sample counts. A conditional diagnostic graph that would otherwise need purpose-built compiled diagnostics thus becomes a few lines of output configuration.

\subsection{Surface-oscillation temporal composition}
\label{sec:oscillation}

The third experiment comes from an investigation of intermittent two-time-step oscillations in near-surface fields. Such an oscillation shows up as successive differences of a field that keep changing sign. For a surface field $f$ with backward difference $b_t = f_t - f_{t-1}$, the product
\begin{equation}
  b_t\,b_{t-1} = (f_t - f_{t-1})(f_{t-1} - f_{t-2})
  \label{eq:oscillation}
\end{equation}
is negative exactly when $f$ has a turning point at step $t-1$. A two-step oscillation therefore makes it negative at every step, and the fraction of steps on which it is negative measures how often $f$ reverses. During that investigation, the backward difference, the second difference $b_t-b_{t-1}$, and this product were written as purpose-built C++ kernels, none of which was adopted in the host model. As expressions, they need no source change:
\begin{verbatim}
aliases:
  - bt1 := f - f.shift(time=1)
field_names:
  - bt2              := bt1 - bt1.shift(time=1)
  - bt1_product      := bt1*bt1.shift(time=1)
  - bt_sign_reversal := mask.where(bt1_product<0)*1.0
\end{verbatim}
Here \texttt{f} is the surface field and \texttt{bt1} is $b_t$. Each \texttt{shift} holds the previous-step value of its own operand, so \texttt{bt1.\bk shift(time=1)} is $b_{t-1}$ and reaches back to $f_{t-2}$ with one-step shifts alone. In a stream that averages over time, as this one does, every expression is evaluated at every step, so each shift is exactly one model step (Sect.~\ref{sec:design}). The indicator \texttt{mask.\bk where(bt1\_product<0)} is 1 where the product is negative and 0 elsewhere, so its time mean is the fraction of steps with a sign reversal; the factor of 1.0 makes it a real-valued field that the output can write. (Shifting \texttt{f} twice, as in \texttt{f.shift(time=1).\bk shift(time=1)}, would not reach $f_{t-2}$, because both shifts are updated at the start of the same step; a two-step lag needs an operation in between, as in \texttt{(f.shift(time=1)*1.0).\bk shift(time=1)}.) Figure~\ref{fig:demos}c shows the sign-reversal fraction of \texttt{T\_2m} over the second day of a two-day ne30pg2 run with a 30\,min step. For \texttt{T\_2m} and \texttt{wind\_speed\_10m}, all three expressions match a line-for-line replay of the original kernels bit for bit, except at the first two steps, where the expressions mark the second difference invalid because it is not yet defined.

\conclusions[Summary and discussion]
\label{sec:conclusions}

A host component model in E3SM can now be asked for a derived diagnostic by writing it down in familiar syntax. The request is an expression over model fields in the output configuration. A model-independent library parses it, and the host model checks it against its vocabulary, translates it into a graph of its compiled generic diagnostics, and evaluates that graph at the end of each step on the in-memory fields, before the stream remaps or accumulates anything. Because each stream sets its own output frequency, such a diagnostic can be sampled every step and written at whatever cadence the question needs, independently of the rest of the output. In three small experiments --- a doubly periodic case, a conditional high-cloud workflow and a surface-oscillation investigation --- the same small set of operators produces horizontal moments, conditional cloud products and a temporal composition. The results agree with every-step reconstructions and with replays of purpose-built kernels, bit for bit or to round-off, at no measurable cost.

The expression system removes the need for a source change per \emph{quantity}, though not per \emph{operator}. The vocabulary belongs to the host model, so a new operator is still a source change, but every quantity built from it afterwards is configuration. The cloud-top operator of Sect.~\ref{sec:design} is an example of how scientists can generalize their specialized diagnostics and compose them within the expression system. Likewise, a quantity that exists only inside a parameterization, such as a process rate, has to be registered as a field once before expressions can use it (Sect.~\ref{sec:contribs}). For now, expressions are evaluated at the end of the step, so they cannot reach the state between two parameterizations, and they act before temporal accumulation, so none can take a stream's accumulated value as an operand. Each diagnostic in a graph also stores its result in its own intermediate field, so computation time and device memory grow with expression depth.

These limits set our next steps for improving and expanding the expression system. The first is kernel fusion. The graph now runs one diagnostic at a time, each with its own pass over memory; fusing a chain into one kernel would remove the intermediate fields, the kernel launches and the extra passes. Fusion is easier behind a typed intermediate representation, which is also the place to canonicalize every subexpression, so that an alias and an inline spelling of the same subexpression (Sect.~\ref{sec:design}) share one diagnostic. The second is other host models. The parser is model-independent and each host declares its own vocabulary, so porting the system to Omega, the C++ ocean component of E3SM \citep{petersen_ocean_2026}, will show how much of that vocabulary carries over; from there, we intend to bring it to the other E3SM components. The third is the vocabulary itself, which we will grow as scientists ask for operators it lacks. Example future capabilities could include spatial sampling, such as output at fixed sites or along the track of an aircraft or a satellite.

Looking ahead, we view this expression system as a way to compress model output. A field that is written and reduced afterwards has already lost whatever the reduction needed from the steps that were not written. An expression applies the reduction while every step is still in memory and writes only the result. The moment stream of Sect.~\ref{sec:dpscream} is thousands of times smaller than the every-step fields it replaces, yet it keeps the horizontal variance that averaging those fields first would discard. Generic lossy compression approximates every value of every field; here the scientist chooses what is lost, and the expression that records the choice travels with the output in its metadata.

Finally, producing training data for emulators is another case of the same output compression. Process emulators need co-located inputs and outputs, tendencies and fluxes, at every step (Sect.~\ref{sec:intro}). Expressions form these quantities on the model's grid, in its units, before anything is averaged, so a training set becomes configuration rather than code. Two future applications follow. The graph that writes a training set could instead hand each sample to a learner running alongside the model, and the emulator would be trained online on state that is never written to disk. In addition, expressions could also supply the targets for an output emulator: a network, trained alongside the model, that maps a reduced core state to the specialized diagnostics that expressions compute from the full state. A simulation would then archive only the core state and the trained network, and specialized output would come afterwards from evaluating the network rather than rerunning the model. If the network learned the operators rather than a fixed list of diagnostics, that output could include quantities nobody requested at run time.

\section{Expression grammar}
\label{app:grammar}

The requests the host model accepts have, in Extended Backus--Naur Form (EBNF), the form
\begin{verbatim}
request = name | name ":=" expr ;  (* ":=" is split off by the stream *)
expr    = term { ( "+" | "-" ) term } ;
term    = unary { ( "*" | "/" ) unary } ;
unary   = "-" unary | call ;
call    = atom { "." name "(" [ arg { "," arg } ] ")" } ;
atom    = name | number | "(" expr ")" ;
arg     = expr | string | name "=" value | cmp ;  (* cmp: where only *)
value   = [ "-" ] number | string | "[" number { "," number } "]" ;
cmp     = expr ( "<" | "<=" | ">" | ">=" | "==" | "!=" ) expr ;
\end{verbatim}
so method calls bind most tightly, then unary minus, then \texttt{*} and \texttt{/}, then \texttt{+} and \texttt{-}, each from left to right, and a comparison binds more loosely than arithmetic: \texttt{qi+qc>1e-5} compares the sum. Names are identifiers as in C other than \texttt{and}, \texttt{or} and \texttt{not} in any letter case, strings take either quote, and redundant parentheses may also enclose any argument, as in the canonical names of Fig.~\ref{fig:dag}. The arguments each method accepts are given in Table~\ref{tab:vocabulary}. \dexpr\ itself also parses the keywords \texttt{and}, \texttt{or} and \texttt{not}, the power operator \texttt{**}, \texttt{=} as an infix operator anywhere, and calls written \texttt{f(X)}; the host model rejects each of these at stream setup.
