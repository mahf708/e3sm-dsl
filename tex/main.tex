\begin{abstract}
We describe a small diagnostic expression language that lets a derived diagnostic be requested in the output configuration instead of added to model source code.
A standalone parser turns the string into a syntax tree; the host model validates it against a vocabulary it owns and lowers it onto its existing compiled diagnostics, which run once per model step on live, device-resident model state, before the stream's remapping and temporal accumulation.
We implement the system in the C++ atmosphere component of the Energy Exascale Earth System Model.
Expression-produced fields match directly compiled equivalents to bit-for-bit or floating-point round-off, reproduce across restart, and add no end-to-end cost separable from the model's own run-to-run variability at the expression depths we test.
Three miniature experiments --- a doubly periodic case, a conditional high-cloud workflow and a surface-coupling debugging investigation --- show that representative diagnostics from each can be written as expressions and evaluated at runtime.
\end{abstract}

\introduction
\label{sec:intro}

An Earth system model is a set of equations, spatially discretized and temporally stepped forward.
The model state comprises tens to a few hundreds of fields on a three-dimensional grid, updated every time step.
Storing the full model state at every time step is impractical due to the sheer volume of data generated.
For example, the latest release of the Energy Exascale Earth System Model (E3SM) has an atmosphere component with 21\,600 columns and 80 levels with a time step of 30 minutes.
This amounts to about $7$\,MB per three-dimensional field per sample in single-precision floating-point format ($21\,600\times80\times4$ bytes).
Carrying $O(100)$ state fields puts a single snapshot near $0.7$\,GB, and writing one every time step for a simulated year ($17\,520$ samples) comes to about $12$\,TB.
Horizontal resolution refinement makes the data volume grow in a roughly cubic manner with respect to the refinement factor \citep{schar_kilometer-scale_2020}, assuming horizontal refinement is uniform and the temporal resolution is modified to ensure stability, while the vertical resolution remains constant.

In practice, the raw archive is never saved in its entirety.
Instead, a carefully chosen subset of the model state is written according to an output list agreed upon in advance, supplemented with developer-written derived diagnostics, at a specified cadence, and at a specified precision.
Customarily, the set of all available output variables is hardcoded in the model and cannot be changed without modifying the source code, and oftentimes changes are inspired by community-driven model intercomparison projects or by specific scientific questions.
It is normally treated as a logistical decision, a question of how much disk is available and for how long, but it is also a scientific one.
The output list acts as an observation operator applied to the simulated trajectory, and it fixes a priori which questions the model output dataset can answer.

The arrangement is comfortable while models have coarse resolution, but at storm- and cloud-resolving resolution, challenges arise due to both the output volume \citep{balaji_requirements_2018} and the questions we want to ask of the model.
A coarse model is evaluated for its mean state, the seasonal cycle, and top-of-atmosphere energy balance, where monthly or daily mean of a fixed field list serves the purpose well enough.
A kilometer-scale model enables further specialized evaluations, e.g., the organization of convection, updraft and downdraft statistics, cloud lifecycle, precipitation and wind extremes, and boundary-layer structure \citep{caldwell_convectionpermitting_2021,donahue_exascale_2024}.
The latter require conditional means, higher moments, distributions, event frequencies, threshold exceedances, and quantities tracked across time steps, which are not captured by simple averages.
They need samples co-located in space and time at the model's own frequency, conditioning on masks the model forms on its own grid, and in some cases state carried from one step to the next.
None of them commutes with the averaging and remapping that make output affordable either, so each one has to be formed at a particular point in the pipeline: a cloud mask diagnosed on the native grid and then remapped is a different quantity from a mask applied after remapping, and a covariance is not recoverable from separately averaged inputs at any cadence.
Where a derived quantity is computed, and in what order relative to averaging and remapping, is therefore part of its definition, and an output list that fixes that order has already fixed the observable.
So the archive has to grow and the archive has to carry different things, and those two pressures do not point in the same direction.

Model output is also increasingly a training set rather than an archive a person reads.
Component and full-model emulators stand in as economical alternatives to physics models; process emulators replace uncertain or expensive parameterizations inside a running model; output emulators handle downscaling, bias correction, or projection onto impact space; and foundation models are fit to corpora assembled from many sources.
Training datasets require higher frequency and different variables than human analysis does --- tendencies, fluxes, co-located pairs, and process-level state --- and they want a great deal of it.
A training set prepared from model output is one more selection applied to the simulated trajectory, and it carries the same property as any other: whatever the preparation discards is not available to the model being trained.

Taken together, these pressures are an argument for rethinking how model output is designed.
In this manuscript, we argue for a system in which a diagnostic is a mathematical expression, a flexible composition of a small set of operators with an algebra over them, evaluated by the model at runtime while the full state is still in memory.
When implemented, such a system allows a scientist to imagine a variable or a product and project it out in a variety of productive ways without touching the source code: instantaneous or averaged, over an arbitrary time period, mapped, masked, reduced, or redefined.

\subsection{Related works}
\label{sec:related_works}

Outside Earth system modeling, other domains reduce before persistence as a matter of course, and several give users an operator algebra over the live state to do it with.
The LHCb experiment reconstructs and selects physics candidates inside its trigger and discards the raw event, retaining an object about an order of magnitude smaller \citep{aaij_comprehensive_2019}.
Molecular dynamics composes on-the-fly computes and time averages, so a study need not write trajectories \citep{thompson_lammps_2022}.
Computational fluid dynamics evaluates user-written field expressions at run time, with dimensions and region masks, and can decline to store the result \citep{weller_tensorial_1998}.
Astrophysics analysis frameworks carry units through recursively defined derived fields \citep{turk_yt_2011}.
Runtime-analysis frameworks provide expression systems, including just-in-time-compiled derived fields \citep{ayachit_paraview_2015,childs_ascent_2022,godoy_adios_2020}.
Compiling a declarative mathematical specification down to domain-specific code is long-established in finite-element software \citep{alnaes_unified_2014}, and separating what is computed from how it is scheduled is standard practice in domain-specific compilers \citep{ragan-kelley_halide_2013}.

Within Earth system modeling, the capability appears at four placements, each further from the model than the last.
Model-integrated diagnostic managers expose a registered catalogue with reductions \citep{valcke_flexible_2012,danabasoglu_community_2020,kern_diagnostic_2016,adams_lfric_2019}, with conditional sampling and budgets available through specialized namelist interfaces \citep{wan_condidiag10_2022} and arbitrary code through plugin interfaces \citep{hartung_icon_2025,kern_diagnostic_2016}.
These sit closest to the state, but what the user selects from is a catalogue of quantities somebody compiles in advance, so a new quantity is a source change.
I/O middleware carries an output algebra on the write path: XIOS provides arithmetic and elementary functions on fields, six temporal operations, and axis and domain transformations \citep{yepes-arbos_evaluation_2022}, MultIO provides configurable in-memory processing pipelines \citep{sarmany_multio_2024}, and ADIOS2 supports writer-side derived variables \citep{godoy_adios_2020}.
Streaming architectures publish model state to external consumers while a simulation runs: nextGEMS makes common data handling and analysis a first-order part of multi-model kilometer-scale development, EVE frames simulation and data services as a federated infrastructure, and the Destination Earth Climate Digital Twin couples high-resolution production with streaming and downstream processing through One-Pass and AQUA \citep{segura_nextgems_2025,stevens_earth_2024,doblas-reyes_destination_2026,grayson_statistical_2025,nurisso_aqua_2026}.
Post-processing on the archive is the furthest placement and the usual one.
Offline analysis is supported by mature tooling in which fields are labeled objects and operators compose over them \citep{zender_analysis_2008,hoyer_xarray_2017,zhang_e3sm_2022}, and a scientist can express essentially any quantity there without touching model source code.
What post-processing does not have is the model state.
It reproduces a quantity exactly whenever that quantity is determined by what is already written, and it cannot when it is not.
The persistence boundary falls between the second placement and the third: I/O middleware still acts on the write path before anything is published, whereas streaming architectures publish to external consumers and post-processing reads an archive that is already written.
Reduction before persistence is the direction the field is moving.

Read against our thesis of Sect.~\ref{sec:intro}, each of its three parts (an algebra, evaluation before the state is published, and operators that are the model's own acting on live model state) exists somewhere, and two of the three are fairly common.
Dedalus and Oceananigans have all three: a user writes an output quantity as an expression, and it is evaluated during the run against the model's own operators, with Oceananigans compiling the composition to a GPU kernel \citep{burns_dedalus_2020,ramadhan_oceananigansjl_2020}.
They obtain it from the symbolic and operator systems of their host languages, Python and Julia, which a compiled production component does not have.
Since several of these systems run while a simulation is running, the distinction is not online against offline.
It is which representation of the state the operator receives, and therefore which code implements the operator: for a quantity whose definition depends on the component's own conventions, its vertical coordinate, its area weights, its masking and renormalization rule, the implementation is part of the definition.
For that reason we follow \citet{childs_terminology_2020} in avoiding ``in situ,'' whose established usage covers analysis over a published mesh representation, and we write ``model-integrated'' or ``in-model'' throughout.

\subsection{Contributions}
\label{sec:contribs}

We implement the system described above in the C++ atmosphere component of E3SM \citep{donahue_exascale_2024}, written with Kokkos for performance portability \citep{trott_kokkos_2022}.
A user writes a derived quantity as an expression over model fields in the output configuration; a standalone parser turns the string into a syntax tree, and the host model validates it against a vocabulary it owns and lowers it onto its existing compiled diagnostics.
The operators are familiar ones for atmospheric modeling: interpolation to levels, pressure surfaces and height surfaces; horizontal, zonal and vertical reduction; vertical derivatives; conditional sampling; histograms; arithmetic; and a one-step temporal shift.
Composed with the stream's own instantaneous, mean, minimum and maximum accumulation, they cover the projections named in Sect.~\ref{sec:intro}.

Our system has four properties as follows.
It is user-defined: the quantity is named in a configuration file, not added to model source code, so asking a new question does not require a review and a merge.
It is in-model: each expression is evaluated once per model step, at the end of the step and inside the component's own output path, against live \texttt{Field} objects and before the stream's remapping and temporal accumulation --- so a quantity can be formed before the reductions that would destroy it, though not between two parameterizations.
It is GPU-friendly: the objects that execute are the model's own Kokkos kernels operating on the same device-resident allocations the model's processes use, so nothing is copied to the host and no second array model is introduced.
It is flexible but bounded: the operators compose freely, while the vocabulary itself is deliberately small, which is a governance property rather than an expressiveness win.

This implementation is a start rather than a finished system.
We do not demonstrate a model-independent language, port the capability to another component yet, implement an optimizer or a typed intermediate representation, or fuse expressions for performance.
Our goal is to integrate this capability in the C++ ocean component of E3SM \citep{petersen_ocean_2026} soon, and from there to the rest of E3SM components.
Additionally, we aim to expand the vocabulary to cover more derived quantities and operations that scientists commonly use in their analyses on an as-needed basis.

\section{Design and implementation}
\label{sec:design}

\emph{Fields as contracts.}
The C++ atmosphere component of E3SM holds its state in \texttt{Field} objects rather than raw pointers.
\begin{equation}
  F_\sigma = (x;\ n, \tau, \sigma)
  \qquad
  \sigma = (g,l,d,u,m)
  \label{eq:field}
\end{equation}
A field $F$ carries numerical storage pointer $x$ together with a name $n$, tracking timestamp $\tau$, and a contract $\sigma$.
The contract contains a grid $g$, a labeled layout $l$, a data type $d$, units $u$, and an optional validity mask $m$.
The contract is not decorative, because field operations must respect the constraints it encodes.
Two fields can be added only if their units agree; multiplying them multiplies their units; a vertical reduction removes a dimension tag; interpolating to a pressure level introduces a mask where the level lies outside the column.
Like prognostic processes in the model, diagnostic processes take fields as input and produce fields as output.
A control driver orchestrates the execution of these processes, ensuring that dependencies are satisfied and that the model advances in a consistent manner.
Because the output reenters the model's field repository, it can be used as input for subsequent processes or diagnostics, enabling a composable workflow without additional machinery.
A diagnostic also hashes the requested output time stamp together with the tracking time stamps of its inputs and skips computation if the hash is unchanged, so a diagnostic shared by several streams at one model time runs once, and a static repository keyed by request name lets a second stream reuse an object the first stream builds.


\emph{Output pipeline.}
The output driver evaluates diagnostics on the source grid, then applies optional vertical remapping, then optional horizontal remapping, then updates the stream's temporal accumulator, then writes through SCORPIO \citep{krishna_scorpio_2025}.
\begin{equation}
  Y = \mathcal{A}_t\,\mathcal{R}_\text{h}\,\mathcal{R}_\text{v}\,\mathcal{D}_\text{e}[X(t)],
  \label{eq:pipeline}
\end{equation}
These stages are defined in Eq.~\eqref{eq:pipeline}, with absent stages resolving to identity.
The written expression controls $\mathcal{D}_\text{e}$ and stream settings control the rest.
Averaging and remapping do not commute with nonlinear operations: a user who writes \texttt{qv*T\_mid} in an averaged, horizontally remapped stream gets $\mathcal{A}_t\mathcal{R}_\text{h}[q_vT]$, which is neither $\mathcal{A}_t[\mathcal{R}_\text{h} q_v\cdot\mathcal{R}_\text{h} T]$ nor $\mathcal{R}_\text{h}\mathcal{A}_t[q_vT]$.
The order is a design decision made to cleanly separate concerns in the output pipeline.
Figure~\ref{fig:arch} places the stages of Eq.~(\ref{eq:pipeline}) against the persistence boundary and names, at the lowering stage, the three demonstrations of Sect.~\ref{sec:demos} and the operators each draws on.
The figure's one piece of encoding is which side of that boundary a stage sits on: above it a stage sees \texttt{Field} objects whose grid, layout, units and mask the component owns, and below it a published archive or stream.
Downstream analysis is not displaced by anything above the line and is drawn with the same weight, because the products retained above it are what downstream analysis then works from.

\emph{Global grammar, local semantics.}
Even though composition is possible in the absence of a formal grammar, it quickly leads to ambiguity and confusion.
Hence, introducing our diagnostic expression parser, \dexpr\,--- a lexer, a \citet{pratt_top_1973} parser, an abstract syntax tree (AST), a renderer that prints an abstract syntax tree back to canonical text, and a call validator.
It is a minimalist C++ library with no dependencies, and it does not know what a field, a grid, or a time step is.
The component decides what means something, through a function registry in which it declares each callable with its name, arity, accepted keywords, and an example of the call as written.
The registry validates itself at construction, such that each example must parse, must call the function that declares it, and must satisfy its own arity and keyword rules, so an inconsistent declaration fails when the registry is built rather than when a user first writes it.
The division is the design's main portable idea: The grammar is global, the semantics are local, and two components can share a parser without sharing a single physics operator.

\emph{Surface syntax.}
The syntax follows xarray \citep{hoyer_xarray_2017} spelling where possible.
An expression written to a file must be named with \texttt{:=}, because the expression itself may not be a valid NetCDF \citep{rew_netcdf_1990} variable name, and expressions in an \texttt{aliases} section are intermediates: built, usable by name, but not written.
\begin{verbatim}
fields:
  physics_pg2:
    aliases:
      - warm_T         := T_mid.where(T_mid>273.15)
    field_names:
      - q_flux         := (qc+qv)*p_mid
      - warm_T_colavg  := warm_T.mean('lev')
\end{verbatim}
The variable \texttt{q\_flux} carries \texttt{(qc+qv)*p\_mid} as its \texttt{alias\_of} attribute.
Operands may be model fields, other expressions, named physics constants such as \texttt{P0} and \texttt{Rgas}, or numeric literals.
Precedence is conventional, so \texttt{qc+qv*p\_mid} means \texttt{qc+(qv*p\_mid)} --- which is in fact rejected at construction due to units mismatch --- whereas \texttt{(qc+qv)*p\_mid} is admissible.
Table~\ref{tab:vocabulary} gives the vocabulary.
For now, there are no loops, user-defined functions, mutation, external state, or dynamic code loading, and every operation has a compiled implementation, a field contract, and a unit test.
The vocabulary is deliberately small at this stage, a governance choice rather than a limit of the design, and we expect it to grow.
Each entry in the table is a primitive $D_k$, one of the operators the diagnostic stage $\mathcal{D}_e$ of Eq.~(\ref{eq:pipeline}) composes, and each is applied in two steps: a signature ($\Sigma_k$) that asks, from the contracts alone, whether a request means anything and what contract its result would carry, and, where that succeeds, the computation of the numbers,
\begin{equation}
\begin{aligned}
  \Sigma_k &: (\sigma_1,\ldots,\sigma_n;\ \theta)
        \rightharpoonup (\sigma'_1,\ldots,\sigma'_m),\\
  D_k(\theta) &: F_{\sigma_1}\times\cdots\times F_{\sigma_n}
        \longrightarrow F_{\sigma'_1}\times\cdots\times F_{\sigma'_m}.
\end{aligned}
\label{eq:ops}
\end{equation}
Fields $F_\sigma$ carry a contract $\sigma$ as defined in Eq.~(\ref{eq:field}); and $\theta\in\Theta_k$ is the primitive's non-field arguments, e.g., the level in \texttt{X.isel(lev=k)}.
The signature does not succeed on requests the model rejects, such as adding two fields whose units differ, and note the output contracts are different from the input contracts, as they are computed by the primitive rather than inherited.
The signature is checked once, on the host, when the expression is lowered at stream setup; the second line is what runs on the device at each output event.
Every primitive registered today has $m=1$, which the diagnostic interface enforces, but nothing in the algebra requires it and we intend to relax that restriction.

\emph{Lowering by name.}
A request reaches the output manager as a string, and the manager splits an optional \texttt{name :=} prefix, tries the remainder through \dexpr, which tokenizes and parses it; the AST is then validated against the model's registry.
Only the root node is translated into one diagnostic class and one parameter list; its operands are rendered back to canonical text and recorded as the diagnostic's input field names, so the ordinary dependency resolver finds them missing from the field manager and sends each through the same factory, which parses it in turn (Fig.~\ref{fig:dag}).
Recursion through names, rather than through a graph object, builds the whole expression graph using no data structure the output manager does not already have.
Canonical rendering is what makes the name a reliable key, such that \texttt{qv > 0.01} and \texttt{qv>0.01} name the same diagnostic when nested, while the top-level request string is kept verbatim because it is also the output variable's name.
Validation is layered so that a failure is reported by the layer that knows why it fails.
This way, \dexpr\ catches malformed syntax, unknown functions, wrong arity, and keyword errors; the model's front end catches operators with no diagnostic, comparisons outside \texttt{where}, and roots that are not fields; construction catches incompatible units, layouts, data types, and grids; and stream setup catches unnamed expressions, duplicate aliases, unresolvable dependencies, and integer output.
No phase silently repairs a request, and there is no algebraic rewriting.
The variable in the file carries the user's output name, the derived units, and an \texttt{alias\_of} attribute holding the requested expression, which is expression-level provenance rather than the fully resolved graph; complete reconstruction additionally requires the stream configuration and the run record.

\section{Demonstrations}
\label{sec:demos}

We use three small experiments to illustrate the diagnostic-expression capability in scientifically recognizable settings.
Two are reduced versions of workflows used in published studies, while the third comes from an internal debugging investigation related to surface coupling.
These experiments are demonstrations rather than reproductions; their duration and resolution are intentionally modest, and the scientific conclusions of the corresponding studies are not re-evaluated here.
All demonstration runs use the C++ atmosphere component of E3SM on NVIDIA A100 GPUs with the Kokkos CUDA backend.

\subsection{Verification and computational cost}
\label{sec:verification}

Regression tests compare masked and conditionally sampled diagnostics with hand-computed values, including empty masks, chained conditions and independent valid-sample counts.
An online product, $\overline{q_vT}$, agrees with an every-step reconstruction to a maximum relative difference of $2.22\times10^{-16}$, one unit in the last place of double precision.
Formed instead from separately averaged inputs, $\overline{q_v}\,\overline{T}$ departs from it by up to $0.64\%$, so the covariance discarded by averaging before multiplication is measurable rather than nominal.
A two-day continuous run and the same run restarted after one day produce identical \texttt{shift} and \texttt{tend} output over all eight common windows.
Repeated requests share a diagnostic graph.
One and two streams requesting the same expression each evaluate the mask and reduction nodes; only the stream-specific accumulation and write work increases.
End-to-end timing likewise resolves no expression overhead above repeated-run variability.

Three moments are retained every step --- $\overline{T}$, $\overline{T^2}$ and $\overline{T}^2$, the overbar a horizontal mean --- and the standard deviation is formed downstream as $(\langle\overline{T^2}\rangle-\langle\overline{T}^2\rangle)^{1/2}$, the angle brackets a time mean.
Squaring the horizontal mean online, rather than squaring the time-mean profile afterwards, is what makes this the time mean of the instantaneous horizontal variance.
(b) The P3 ice mixing-ratio tendency from the miniature high-cloud workflow, sampled in cloudy sky and over all sky: the two requests differ by one method call, and the cloudy-sky profile is larger than the all-sky one by more than an order of magnitude through most of the troposphere, so the two are drawn on separate scales.
The shaded band marks the levels at which the cloud mask admits samples, read from the stream's own valid-sample count.
(c) The fraction of steps at which successive surface-temperature differences reverse sign, formed with one-step shifts and arithmetic and written as a global field.
Each ne30pg2 cell is drawn as itself, so the panel carries no interpolation the model did not perform.
The panels demonstrate spatial reduction, conditional sampling and temporal composition, respectively; none is used to draw a new conclusion about the simulated system.}
\label{fig:demos}
\end{figure*}

The first experiment uses a $50\times50$\,km doubly periodic radiative--convective-equilibrium domain with 100 physics columns, 128 vertical levels and a 100\,s time step.
It is a reduced instance of the doubly periodic configuration of \citet{bogenschutz_high_2025}.
We request the horizontal temperature profile \texttt{T\_mid.\bk mean('col')}, a mass-weighted column water-vapor quantity \texttt{qv.\bk mean('lev',\bk weights='dp')}, and the horizontal second moment \texttt{(T\_mid*T\_mid).\bk mean('col')}.
The requested reductions execute without a purpose-built diagnostic class and produce the expected vertical products (Fig.~\ref{fig:demos}a).
The online mean and second moment agree with reductions of the every-step three-dimensional reference.
The example exercises reductions over model columns and levels, weighted reduction and composition of a reduction with arithmetic.
Limited-domain studies such as this one are often aimed at domain-mean quantities, which the online reductions supply without writing a single three-dimensional field.

\subsection{Conditional high-cloud products}
\label{sec:cess2}

The second experiment is a one-day instance of the conditional high-cloud workflow used in the SCREAM analyses of \citet{beydoun_dissecting_2021} \todo{cite 2026 paper}.
The full study examines the response of tropical anvil cloud to surface warming over 19-month integrations.
We instead select representative model-side operations from that workflow: the cloud condition $q_i+q_c>10^{-5}$, conditional samples such as \texttt{qi.where(qi+qc>1e-5)}, a conditional vertical derivative, and a product of conditionally sampled quantities.
The expressions are evaluated every model step and accumulated over a 12\,h window.
The cloud mask, conditional samples, derivative and products all execute from the output configuration and produce vertical high-cloud products, such as the conditioned P3 ice tendency in Fig.~\ref{fig:demos}b.
Dropping the \texttt{where} clause from that same request leaves an all-sky profile smaller by more than an order of magnitude through most of the troposphere.
This result is deliberately limited to capability: it shows that a conditional diagnostic graph that would otherwise be assembled from named compiled diagnostics can be represented using \texttt{where}, comparisons, arithmetic, vertical derivatives and reductions.
For the scientific analysis and interpretation of this class of conditional high-cloud diagnostics, see \citet{beydoun_dissecting_2021} \todo{cite 2026 paper}.

\subsection{Surface-oscillation temporal composition}
\label{sec:oscillation}

The third experiment uses an existing short surface-coupling case to exercise temporal composition.
For a surface field $f$, we define a backward difference \texttt{b := f - f.\bk shift(time=1)}, from which a second difference and the product of successive differences follow.
These are the generic forms of diagnostics that exist as dedicated C++ classes, written during an investigation of intermittent two-time-step behavior in near-surface fields.
We compare the expressions with those reference kernels where a direct counterpart is available.
The backward tendency written as \texttt{f.tend()} agrees bit for bit with its compiled counterpart over $1\,179\,648$ values on both tested backends.
The second difference, product of successive differences and sign-reversal indicator are requested as:
\begin{verbatim}
aliases:
  - bt := f - f.shift(time=1)
field_names:
  - bt2         := bt - bt.shift(time=1)
  - bt2_product := bt*bt.shift(time=1)
  - alternating := mask.where(bt*bt.shift(time=1)<0)*1.0
\end{verbatim}
The three expression products agree bit for bit with direct replays of the corresponding compiled kernels over $17\,664$ values for each of \texttt{T\_2m} and \texttt{wind\_speed\_10m}.
Figure~\ref{fig:demos}c shows one resulting diagnostic product: the fraction of samples in which successive differences reverse sign.
The example exercises aliases, one-step history, arithmetic, comparisons and conditional sampling, and shows that such a diagnostic can be assembled from generic operators.

\conclusions[Summary and discussion]
\label{sec:conclusions}

E3SM can now be asked for a derived diagnostic by writing it down in familiar syntax.
The request is an expression over model fields in the output configuration; it is parsed outside the model, validated and lowered by the model against a vocabulary the model owns, and evaluated once per step on live \texttt{Field} objects before the stream remaps or accumulates anything.
The verification runs show that this route produces the same numbers as the compiled route and survives restart, at no cost that is separable from the model's own run-to-run variability.
The three demonstrations show that it reaches diagnostics of recognizably different kinds --- a spatial reduction and a second moment, a conditional high-cloud workflow, and a one-step temporal composition --- from the same small operator set.

The vocabulary is small and bounded; it belongs to the host model, so a genuinely new operator is still a source change; what the expression system removes is the need for a source change per \emph{quantity}, not per \emph{operator}.
For now, expressions are evaluated at the end of the time step and inside the output path, so they reach model state before the reductions that would destroy it but not between two parameterizations.
Each node of a lowered graph materializes its own intermediate field, so both time and device memory grow with expression depth, and deep graphs are not free.
The three experiments are capability demonstrations at reduced duration and resolution; they reproduce neither the integrations nor the conclusions of the studies they are drawn from.

Those limits set the work we intend next.
The clearest is a diagnostic kernelizer: the lowered graph is currently executed node by node, and fusing a chain into a single sweep would remove both the per-operation intermediates and much of the per-operation time, turning expression depth from a cost into a compiler concern.
That in turn is easier to do behind a typed intermediate representation, which would also give a place for an optimizer to eliminate common subexpressions across streams rather than only sharing whole graphs.
We also intend to port the capability to the C++ ocean component of E3SM \citep{petersen_ocean_2026}, which is the first real test of how much of the grammar is component-neutral and how much is atmosphere-specific, and to grow the vocabulary as scientists ask for operators it does not yet have.
